# Blender asset pipeline

Every IronFlag model is **generated by Python, not modelled by hand**. There are no
`.blend` files to maintain: `blender/assets/*.py` is the source of truth, and
`.glb` files in `unity/Assets/RF/Art/Models/` are build output that happens to be
committed.

This exists because the asset spec restricts everything to primitives, flat shading
and vertex colors — which is tedious by hand and trivial in script — and because a
scripted asset can be re-derived, diffed and reviewed like any other code.

---

## Running a build

```bash
./build.ps1                 # rebuild every asset into the Unity project
```

```bash
./build.ps1 -Asset Jeep     # rebuild just the assets matching "Jeep"
```

```bash
./build.ps1 -List           # list known asset names
```

`build.sh` is the same wrapper for POSIX shells. Both find Blender automatically;
set `IRONFLAG_BLENDER` to override. From inside Unity, **Tools > IronFlag > Rebuild
All Art from Blender** runs the identical command and re-imports the result.

Under the wrappers it is just:

```bash
blender --background --factory-startup --python blender/build.py -- --asset Jeep
```

## Adding an asset

1. Copy `assets/vehicle_jeep.py` to a new module in `assets/`.
2. Build the shape out of `rf.primitives` calls, coloring from `rf.palette`.
3. Export the `BUILDERS` dict mapping full asset name to builder function.
4. Run `./build.ps1 -Asset <YourName>` and check the triangle count it reports.

`build.py` discovers modules automatically — there is no registry to update. It
rejects names that break the `RF_<Category>_<Name>_<State>` rule before exporting,
so a typo fails the build instead of surfacing later as a missing model in Unity.

A builder must:

- call `scene.begin(ASSET_NAME)` first, which wipes the file and opens a
  collection named after the asset;
- return the **root object**, named exactly the asset name (the build asserts this);
- parent any moving parts to that root;
- hand any non-body group to `attach_group` so it becomes its own child object.

### Destruction states

One module per family, one builder per state:

```python
BUILDERS = {
    "RF_Structure_FlagTower_Intact": build_intact,
    "RF_Structure_FlagTower_Damaged": build_damaged,
    "RF_Structure_FlagTower_Destroyed": build_destroyed,
}
```

Share a `_base_shape()` helper between states so the damaged version is visibly the
same building, and tint the broken parts with `palette.CHARRED` / `palette.SCORCH`
so every destructible in the game chars the same way.

## Conventions this pipeline locks in

These are decisions the asset spec did not pin down, resolved once here so every
asset behaves the same in Unity.

**Vehicles are built facing -Y.** The glTF exporter maps Blender -Y to Unity +Z, so
a model authored nose-first toward -Y drives forward in Unity with no manual
re-orientation. Do not "fix" orientation by rotating the object.

**Left and right are counter-intuitive while authoring.** Facing -Y with +Z up means
`right = forward x up = -X`, so the vehicle's *left* side is at **+X** in Blender.
The glTF importer mirrors X on the way into Unity, so +X here really does end up on
Unity's left. Name parts by the vehicle's own left/right, not by which way they look
on your screen.

**Origins sit on the ground, centred on the footprint.** Unity's transform pivot is
then the contact point, which is what vehicle controllers and structure placement
both want.

**Anchors are separate objects, named, with their origins where Unity needs a point.**
Three assets carry them and they all work the same way: the bunker's `LiftPlatform`
and `Helipad`, every vehicle's `Muzzle`, and each state of the flag tower's
`FlagMount`. Unity reads the object's *origin* rather than a number in code, so
moving where a vehicle appears, where a round leaves, or where a flag stands is an
art change and nothing else. Keep them out of `join` (use `set_pivot` then `attach`),
and do not rename one without renaming its constant on the C# side — the code falls
back to a guess and nothing warns.

**Material groups.** Nearly all color is vertex color on a single material, so a
whole vehicle can be one mesh and still carry a dozen palette colors. A separate
material is only added when Unity needs to *change* something a baked color cannot
express:

| Group | Material | Child object | Why it is separate |
|---|---|---|---|
| `body` | `RF_Flat` | *(the root)* | Vertex-colored. Everything that is just a color. |
| `team` | `RF_TeamAccent` | `TeamTrim` | Unity assigns a per-team material |
| `lightFront` | `RF_LightFront` | `LightsFront` | Emission is a material property; a vertex color cannot glow |
| `lightRear` | `RF_LightRear` | `LightsRear` | Same, plus brake/damage states |
| `muzzle` | `RF_Muzzle` | `Muzzle` | A known renderer to anchor weapon VFX to |

Pass `group=material.LIGHT_FRONT` to any primitive, then hand the parts to
`p.attach_group(parent, group, parts)`. The parent is usually the asset root, but a
group that belongs to a moving part hangs off that part instead - the tank's muzzle
is a child of `Turret`, so it traverses with the gun.

**Every vehicle carries a `Muzzle`**, and where it hangs decides how that vehicle
fights. The tank's and the ASV's are children of the part that traverses, so their
guns aim independently of the hull; the jeep's cowl launcher and the helicopter's
chin gun hang off the root and are fixed forward, so those two have to point their
nose at what they want to hit. Unity measures the firing point off this object's
geometry rather than its origin, so a longer barrel needs no code change - see
`VehiclePrefabBuilder.MuzzleTip`. A vehicle exported without a `Muzzle` still builds,
and warns that it will not be able to fire.

Each group becomes its **own child object**, not an extra material slot on the hull
mesh. A renderer whose submeshes mix glTFast's Shader Graph material with a
Unity-side material does not reliably draw the second one - see
`SCAFFOLDING_NOTES.md`. One object, one material is unambiguous, and unused slots are
stripped on join.

This is what "team color goes on decals only" means mechanically: recoloring a team
replaces a material, never a mesh.

**Static parts get joined; moving parts stay separate.** Anything Unity animates —
wheels, turrets, rocket launchers, rotors — stays its own object with its origin on
its axis of rotation (`primitives.set_pivot`), parented to the root. Everything else
is joined into a single mesh so a prop is one draw call.

**Transforms are already applied.** Primitives generate their geometry directly in
world space, so objects export at identity without anyone remembering Ctrl+A.

## Asset inventory

Every asset in `return-fire-homage-asset-spec.md` is built: **26 `.glb` files** from
ten modules. Two of them are the ones to copy when adding more - `vehicle_jeep.py`
for anything with moving parts and team trim, `structure_flagtower.py` for anything
with destruction states.

| Asset | States | Moving parts | Team trim |
|---|---|---|---|
| `RF_Vehicle_Jeep` | - | 4 wheels | yes |
| `RF_Vehicle_Tank` | - | turret | yes |
| `RF_Vehicle_ASV` | - | launcher | yes |
| `RF_Vehicle_Helicopter` | - | main + tail rotor | yes |
| `RF_Structure_Bunker` | - | - | yes |
| `RF_Structure_FlagTower` | intact / damaged / destroyed | - | no |
| `RF_Structure_DepotFuel` | intact / damaged / destroyed | - | no |
| `RF_Structure_DepotAmmo` | intact / damaged / destroyed | - | no |
| `RF_Prop_Bridge` | intact / destroyed | - | no |
| `RF_Prop_BuildingA` | intact / damaged / destroyed | - | no |
| `RF_Prop_BuildingB` | intact / damaged / destroyed | - | no |
| `RF_Prop_Tree` | intact / damaged / destroyed | - | no |
| `RF_Prop_Flag` | - | - | banner only |

Vehicles match the spec's dimension table, and the silhouette contract it implies
holds on **hull** width - rotors excluded, since a rotor disc is not a hull:
tank 3.19m, ASV 2.80m, jeep 1.80m, helicopter 1.34m fuselage under a 4.4m rotor.
The tank is also the tallest and longest, which is what keeps it reading as the
heavy of the roster.

## Layout

| Path | Role |
|---|---|
| `build.py` | Headless entry point: discovers assets, validates names, exports |
| `build.ps1` / `build.sh` | Wrappers that locate Blender for you |
| `rf/palette.py` | The fixed color palette, as linear RGBA |
| `rf/primitives.py` | Box, wedge, pyramid, cylinder, cone + join/pivot/parent helpers |
| `rf/material.py` | The two shared materials and vertex-color painting |
| `rf/scene.py` | Per-asset scene reset, collections, selection |
| `rf/export.py` | The fixed glTF export settings |
| `rf/naming.py` | `RF_<Category>_<Name>_<State>` validation |
| `assets/vehicle_*.py` | The four vehicles; jeep is the reference for moving parts |
| `assets/structure_*.py` | Bunker, flag tower, both depots |
| `assets/prop_*.py` | Bridge, two buildings, tree |
