# S1 — Groundwork

The step's goal, deliverable and verify are in [`plan.md`](../plan.md) §3, with a status line that links here.
Section references (§n) are to the design, [`by_galactic_accord_gdd_v0.3.md`](../../by_galactic_accord_gdd_v0.3.md).

*S1 status (2026-10-25): done.* The WPF client and the console game are gone; the console app is the soak
harness only, and the solution builds and tests on Linux. **The test suite went from 6 min 49 s to a few
seconds:** plain `dotnet test` runs 58 fast tests in about 2 s (4–5 s wall, with the test host's start-up),
and `dotnet test --filter Category=Soak` runs 22 soak-length tests in 36 s. Most of the old cost was not
path-finding: the board query walked and sorted every contract ever posted, so each heartbeat cost more as
history grew and run time was quadratic in run length. Fixing that made a million-tick soak 8–13 times faster
(57.1 s → 4.5 s for seed 20260619, 34.8 s → 4.0 s for seed 42), and caching paths took another 40% off.
The simulation's results are unchanged: soak telemetry is identical before and after, at a million ticks,
for both seeds. Game time now reads as dates and durations ("Day 4 · 14:00", "in 1d 6h").

## What was built

- **Retired** (design D23): the WPF client (`src/ByGalacticAccord.Wpf/`, its screenshot `docs/screenshot.png`)
  and the console game (`src/ByGalacticAccord.Cli/Game.cs`). `Program.cs` keeps `soak` (now the default
  command) and `help`; `play` is an unknown command. `PlayerActions` stays in the engine: it is the player's
  command path through the same code the AI uses, and S3 reworks it.
- **The board query is incremental** (`SimulationContext.OpenContracts`). It kept every contract in one
  dictionary and, on each call, filtered all of them and sorted the open ones. It is called on every
  consumer heartbeat for each short good and on every hauler heartbeat. At 500k ticks there were 15,932
  contracts and about 3 open at a time. The context now keeps a list of contracts that were open when last
  looked at, in id order; enumeration prunes the ones that have closed and yields a snapshot. This relies
  on a contract never returning to Open or Negotiating once it leaves them, which holds in this engine
  (only the constructor sets Open). Enumeration starts when the caller first moves, as before, and the
  snapshot means callers can still sign contracts while iterating.
- **Paths are cached** (`SimulationContext.FindPath`): each (from, to) pair is solved once by the existing
  Dijkstra (`SolvePath`) and memoised. Adding a location or a route clears the cache. Plans are immutable;
  `RoutePlan.Path` is now an array.
- **Game time** (`Simulation/GameTime.cs`, §8.3, D21): one tick is one game hour and tick 0 is Day 0 · 00:00.
  `Day`, `HourOfDay`, `At(day, hour)`, `Days(n)`; `FormatDate` ("Day 4 · 14:00", negative days as
  "Day −410" with a typographic minus, as in the mockup), `FormatDuration` ("1d 6h", "2d", "9h", "0h";
  negative durations throw) and `FormatRelative` ("in 1d 6h", "3h ago", "now"). The soak harness prints
  the date beside the tick, and the invariant tests' failure messages carry it. The world already used
  hours (the §15.2 route lengths, a 24-tick heartbeat), so no tuning changed.
- **Fast and soak tests** (§20.3). Long-horizon tests carry `[Trait("Category", "Soak")]`
  (`TestWorld.Category`, `TestWorld.Soak`), and the test project sets `VSTestTestCaseFilter` to
  `Category!=Soak` unless a filter is given, so plain `dotnet test` is fast. Each world-run check has a
  fast variant at `TestWorld.FastTicks` (20,000 ticks, about 833 game days) and keeps its long variant:

  | Check | Fast | Soak |
  |---|---|---|
  | Same seed, same state (3 seeds) | 20k | 150k |
  | Stepped replay matches one run | 20k in 1k steps | 120k in 5k steps |
  | Different seeds diverge | 20k | — |
  | Invariants at every checkpoint (4 seeds) | 20k, every 1k | **1M**, every 10k (was 300k) |
  | Credits conserved, escrow reconciles, nobody below ₵0 (2 seeds each) | 20k | 250k |
  | The economy comes alive (3 seeds) | 20k | 200k |
  | Money supply stays in band (3 seeds) | — | 1M |
  | No monopoly (2 seeds) | — | 500k |
  | The frontier is reachable | 20k | — |

  The fast thresholds are the soak ones: at 20k ticks every seed fulfils 748–818 contracts against a
  required 500, with 4–13 breaches against an allowed tenth.
- **New tests:** `GameTimeTests` (dates, durations, relative times, day and hour round trip),
  `DomainTests.FindPath_is_cached_until_the_route_graph_changes`,
  `DomainTests.OpenContracts_lists_open_contracts_in_id_order_and_drops_closed_ones`.
- **The README** describes the new direction: the design, the plan, the logs, the current build and how
  to run it.

- **Same results.** The soak harness's full telemetry (credit supply, faucet, sinks, contracts by status,

- **Where the time went** (a probe running seed 20260619 in 100k-tick chunks, Release, two runs each on a

  from 6.8 s to 4.1 s.
- **Linux:** `dotnet build` of `ByGalacticAccord.slnx` succeeds with no warnings (warnings are errors here).

## Decisions taken in code

- The board's speed-up is a pruned list rather than an index updated on every status change, because
  `Contract` changes its own status and has no reference to the world. If a later step lets a contract
  go back to Open (for example a haggle that falls through, S5), it must re-add the contract to the
  list, or switch to an index the status changes update.
- The path cache is cleared on any change to locations or routes rather than tracking which pairs a change
  affects. Routes are static in Slice 1; if routes ever change during a run (blockades, Slice 5), the same
  clearing covers it.
- Game-time words ("Day", "in", "ago", "now") are in the engine for now. S2's template layer (§11.5)
  owns interface text and may move them into its resource files.
- Money-supply and monopoly checks are soak-only: they are about long-run drift and mean little over 833
  days. The invariant soak now runs a million ticks, as the later steps' checks do.
- `dotnet test` is fast by default through the test project's `VSTestTestCaseFilter`, so nobody has to
  remember a filter; a command-line `--filter` replaces it.

## Gotchas

- **Don't time runs while another test run is going.** With the baseline suite still running, the cached
  build looked 15% slower than the uncached one. Measured again on a quiet machine, the cache is 40% faster.
- The old diagnosis in the plan's defect table (Dijkstra per contract, per ship, per heartbeat) was half
  of it; the board query was the larger, growing cost. The plan's row now names both.
- An XML comment in a `.csproj` cannot contain `--`, so the filter comment doesn't spell out `--filter`.
- The repository's `.gitignore` ignores every `log/` folder (a Visual Studio rule for build logs), which
  would have left these logs out of git without a word. `ByGalacticAccord/.gitignore` re-includes this
  project's `log/` only.
- The cloud container has no .NET SDK; it was installed with `dotnet-install.sh --channel 10.0` into
  `/root/.dotnet`.
- graphify is not installed in the container, so `graphify-out/` still described the v0.2 build (with the
  WPF client and the console game). *Since 2026-10-26 the project has no graph: [`CODEMAP.md`](../CODEMAP.md)
  replaced it.*

## Next: S2, the Blazor client

- **Speed for WebAssembly (risk R4).** The engine runs about 240,000 ticks a second in Release on desktop
  .NET (a million in about 4.1 s). At 16× the client needs 16 ticks a second, so even a much slower
  WebAssembly runtime leaves a wide margin; S2 should still measure it, as R4 asks.
- **What still grows with history:** the contract dictionary (contracts are never archived) and
  `TotalEscrowHeld`, which walks every contract and runs on each inflation check (every 400 ticks) and
  in `Invariants.Check`. Neither matters at these sizes; a client that keeps a long game open may want
  settled contracts archived.
- Use `GameTime` for every date and duration the client shows.
- There is no player-facing build left, so S2's client is the first way to see the game again.
